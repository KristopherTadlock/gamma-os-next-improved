# Engine protocol (app ⇄ `thimsy-installer`)

The Flutter app never talks to devices or parses firmware itself. It runs the
bundled engine binary, `thimsy-installer` (`thimsy-installer.exe` on Windows),
which sits next to the app executable (`<app dir>/engine/thimsy-installer`),
and reads **JSON Lines** from its stdout. One JSON object per line. Stderr is
free-form log text for the diagnostic bundle. Exit code 0 = success, 1 = the
command failed (see `error`), 2 = the command line itself was wrong (clap's
usage text on stderr, no JSON at all).

Every command accepts `--json`. Without it, output is human-readable.
Every command accepts `--lang CODE` (Thimsy's codes: `en ar da de el es fi fr
he it ja ko nb nl pl pt ru sv th tr zh-cn zh-tw`; Flutter forms such as
`zh_TW` are accepted). Stage titles, progress labels, prompts, hints, guide
steps, profile text (names, summaries, emulator and app names and systems,
core systems), artifact notes, driver details and the "use Windows" message
come back translated; anything without a translation stays English. Error
`message`s are always English: show them as details under a title the app
picks for the error `code`.

## Samples

`installer/docs/protocol-samples/*.jsonl` are real engine output, one file
per case, regenerated by the engine's tests (`THIMSY_UPDATE_SAMPLES=1 cargo
test samples` in `installer/engine`; plain `cargo test` fails when they're
stale). Temporary paths are replaced by `<workspace>` / `<fixture>`, times by
`run-<time>` / `<time>`, and only each progress label's final event is kept
(the others depend on timing). Keys within a line are sorted. The build and
flash cases use the engine's synthetic test device (`testdev`); the others
the real catalog.

| File | Command |
|---|---|
| `catalog.jsonl` | `catalog` |
| `resolve-rg-cube-heavy.jsonl` | `resolve --device anbernic-rg-cube --profile heavy` |
| `space.jsonl`, `space-fat32.jsonl` | `space` (500 GB free; the same on a FAT32 drive) |
| `build.jsonl` | `build` |
| `flash-dry-run.jsonl` | `flash --mode full --dry-run` |
| `prepare.jsonl` | `prepare --mode full` |
| `flash-full.jsonl` | `flash --mode full`, after `prepare` |
| `error-wrong-device.jsonl` | `flash`, another device's partition table |
| `error-device-not-found.jsonl` | `flash`, the device never shows up in download mode |
| `error-full-install-needed.jsonl` | `flash --mode update`, the device runs another base |
| `error-busy.jsonl` | `build` while another run holds the workspace |
| `clean-dry-run.jsonl` | `clean --dry-run` after the flashes above |
| `detect.jsonl` | `detect` with the RG Cube in download mode |
| `drivers-failed.jsonl` | `drivers --install` on Windows, UAC prompt declined |

## Common event objects (streaming commands)

```json
{"type":"stage","stage":"fetch","title":"Downloading"}
{"type":"progress","stage":"fetch","label":"Downloading RG_Cube_GammaOS_Next_Full_v1.2.7z.001","done":123,"total":456}
{"type":"log","level":"info","message":"…"}
{"type":"prompt","id":"enter_download_mode","title":"…","body":"…","image":null}
{"type":"error","code":"device_not_found","message":"…","hint":"…"}
{"type":"result","ok":true, "...": "command-specific fields"}
```

- `done`/`total` are bytes; `total` may be 0 when unknown. Progress events
  are rate-limited (about 5 a second), but the one with `done == total`
  always arrives. `label` is translated, with the file or partition name
  filled in.
- `log` lines are for the diagnostic bundle (`level` is `info` or `warn`);
  don't parse them.
- `prompt` asks the user to do something physical (hold a key, plug in). The
  engine keeps going on its own once it sees the device; the app just shows the
  prompt until the next `stage`/`result`.
- `error.hint` is translated (or null); `error.message` is English detail.

### When the last line is a `result`

- `build`, `flash`, `unlock`, `drivers` and `clean` (the streaming commands)
  always end with a `result` line in JSON mode: `{"type":"result","ok":false}`
  right after an `error` (plus `status`/`detail` for `drivers`, below).
- `catalog`, `resolve`, `space` and `detect` print one line of their own type
  (`catalog`, `plan`, `space`, `devices`) on success; on failure only an
  `error` line, and exit 1. No `result`.
- `detect --watch` prints a `devices` line whenever the list changes and
  runs until killed; an `error` line ends the watch (exit 1).
- A usage error (unknown flag, missing `--mode`) prints no JSON (exit 2).

## Commands

### `catalog --json`
One line:
```json
{"type":"catalog","version":"0.1.0-test2","release":"Thimsy 1.0a","engine":"0.1.0","host":"linux",
 "devices":[{
  "id":"anbernic-rg-cube","name":"Anbernic RG Cube","maker":"Anbernic",
  "soc":"Unisoc T820","display":"720×720","status":"testing",
  "support":{"build":"verified","boot":"qualified",
             "install":{"windows":"automated","linux":"automated","macos":"untested","android":"none"}},
  "notes":["…"],"blocks":["…"],"host_message":null,"buildable":true}],
 "profiles":[{"id":"light","name":"Light","summary":"…","available":false},
             {"id":"medium","name":"Medium","summary":"…","available":false},
             {"id":"heavy","name":"Heavy","summary":"…","available":true}]}
```
- `version`: the catalog's version; `release`: the Thimsy release it builds;
  `engine`: this engine's version; `host`: `windows|macos|linux|android`.
- `install` values: `automated`, `guided`, `untested`, `none`.
- `host_message` (per device): set when this computer can't install the
  device ("… Run Thimsy Installer on a Windows PC to install it."), else null.
- `buildable`: this version can build an image for the device at all
  (profiles may still be unavailable: see `profiles[].available`).

### `resolve --device ID --profile P [--set KEY=VALUE]... --json`
One line:
```json
{"type":"plan","device":"anbernic-rg-cube","device_name":"Anbernic RG Cube",
 "profile":"heavy","profile_name":"Heavy","available":true,"unavailable_reason":null,
 "host":"linux","install":"automated","host_message":null,
 "emulators":[{"id":"ppsspp","name":"PPSSPP","systems":"PSP","included":true,"reason":null}],
 "cores":[{"id":"mgba","system":"Game Boy Advance","default":true}],
 "apps":[{"id":"brave","name":"Brave (default browser)","included":true,"reason":null}],
 "excluded":[{"id":"armsx2","name":"ARMSX2","reason":"needs an ARMv8.2 CPU"}],
 "settings":[{"key":"nano.theme","value":"esde","source":"profile","reason":null}],
 "download_bytes":4630452770,"disk_bytes":20460997435,
 "partitions_full":["misc","trustos_a","…","splloader_bak"],
 "partitions_update":["logo","fbootlogo","vendor_boot_a","vendor_boot_b","super"],
 "erases_full":["userdata","metadata"],
 "partitions":["logo","fbootlogo","vendor_boot_a","vendor_boot_b","super"],
 "wipes_data":true,
 "journeys":{
   "first_time":{"title":"First time installing custom firmware","body":"…","unlock":true,"modes":["full"],"update_note":null},
   "returning":{"title":"Already unlocked: install new firmware","body":"…","unlock":false,"modes":["update","full"],
                "update_note":"Keeps your data. Only when …"}},
 "connect_first":false,
 "guides":{
   "backup":[{"title":"…","body":"…","link":null}],
   "unlock":{"route":"automated|guided|none","steps":[{"title":"…","body":"…","link":null}]},
   "download_mode":[{"title":"…","body":"…","link":null}],
   "first_boot":[{"title":"…","body":"…","link":null}]}}
```

- `device_name`, `profile_name`: display names (`profile_name` translated).
- `host`, `install`: this computer and the device's install support on it.
- `host_message`: set when this computer can't install the device; show it and
  offer only build-and-export.
- `emulators[].name`/`systems`, `apps[].name`, `excluded[].name`,
  `cores[].system`: translated.
- `download_bytes`: everything this build downloads. `disk_bytes`: peak disk
  use of building and then flashing on an empty workspace, keeping the
  downloads; exactly what `space` reports as `need` for an empty workspace
  without `--delete-downloads`.
- `partitions_full` / `partitions_update`: the device partitions a full
  install / an update writes; `erases_full`: what a full install erases
  (updates erase nothing). They come from the device's recipe (no firmware
  exists before the build), and `flash` refuses to start when the firmware
  would write anything else, so what the plan showed is what gets written.
  `partitions` is the same as `partitions_update`, for older apps.
- `journeys`: ask whether the device has had custom firmware before. First
  time → show the unlock step and flash with `--mode full`. Returning → skip
  unlocking; offer `--mode update` (keeps data) and `--mode full`.
- `connect_first`: whether the device must be connected in its flashing mode
  before installing starts. False for Unisoc download mode (it only lasts a
  few seconds unless a tool is already waiting): the user connects it once
  `flash` shows the `enter_download_mode` prompt.

### `space --device ID --profile P --workspace DIR [--import PATH]... [--delete-downloads] --json`
Run before `build`; don't start the build when `ok` is false.
```json
{"type":"space","need":20460997435,"free":500000000000,"ok":true,"reason":null,"hint":null,
 "build_need":12970303164,"flash_need":20460997435,"cached":0,"imported":0,"downloads":4630452770}
```
- `need` is the larger of `build_need` (downloads still missing plus the
  working image, with 5% headroom) and `flash_need` (the finished image, the
  partitions flashing unpacks next to it, and the new cache files unless
  `--delete-downloads`).
- `--import`: the same files and folders `build --import` will get. A picked
  device pack (or all its parts) or unpacked official firmware is used where
  it is and isn't counted as a download or as disk use; files found by name
  and size in a picked folder are copied into the cache, so they count as
  disk use but not as downloads. `imported`: download bytes the picks stand
  in for; `cached`: download bytes already in the workspace's cache;
  `downloads`: every download the build uses, per the catalog.
- `free`: free bytes on the drive of the workspace (its first existing
  folder when it doesn't exist yet); 0 when it couldn't be checked.
- `reason` when `ok` is false: `fat32` (the drive is FAT32 and the build
  needs a file over 4 GiB), `probe_failed` (the free space couldn't be
  checked: never treated as enough) or `not_enough_space`; `hint` is the
  translated advice for it (else null).

### `clean --workspace DIR [--downloads] [--image] [--scratch] [--backup] [--path PATH]... [--dry-run] --json`
```json
{"type":"result","ok":true,"freed":0,"items":[
  {"kind":"downloads","path":"…/cache/fw.7z.001","bytes":382435},
  {"kind":"image","path":"…/jobs/anbernic-rg-cube-heavy/out","bytes":7722216910},
  {"kind":"backup","path":"…/jobs/anbernic-rg-cube-heavy/backup/run-20261112-171443","bytes":72351744,
   "info":{"device":"anbernic-rg-cube","device_name":"Anbernic RG Cube","partition_table_sha256":"…",
           "time":"2026-11-12T17:14:43Z","mode":"full","engine":"0.1.0"}}]}
```
- `items` lists what was there before cleaning; `freed` is bytes removed.
- Only what the engine made is ever listed or removed: in `cache/`, files
  the catalog names (and their `.partial`, `.partial.json`, `.import`,
  `.ok`, `.tmp` leftovers), and in `jobs/`, folders named
  `<device>-<profile>` for catalog devices and profiles (their `work`,
  `flash`, `out` and `backup` contents). Anything else in the workspace is
  left alone.
- `kind`: `downloads`, `scratch` (unfinished downloads, the build's `work`
  folder, flashing's `flash` folder), `image` (the finished image; removing
  it also removes `job.json`, so the job can't be flashed) or `backup`.
- Backups are listed per run folder (`<job>/backup/run-<UTC time>`), each
  with `info`: its `device.json` (which device and partition table it came
  from, when, and in which mode), when it has one. Keep backups unless the
  user insists: only `--backup` or `--path` removes them. `--scratch` first
  moves any backup an earlier engine version left in a job's `flash` folder
  into its `backup` folder (listed as a `backup` item until then).
- `--path PATH` (repeatable): remove exactly these items (paths from
  `items`), e.g. after the user confirmed one backup run. A path that isn't
  a listed item fails with `bad_input` and nothing is removed.
- Without `--dry-run`, `clean` holds the workspace lock (see `busy`).

### `build --device ID --profile P --workspace DIR [--import PATH]... [--set K=V]... [--delete-downloads] --json`
Streams stages `plan`, `fetch`, `extract`, `assemble`, `validate`, `publish`.
Final:
```json
{"type":"result","ok":true,"job":"DIR/jobs/anbernic-rg-cube-heavy","image":"DIR/jobs/…/out/anbernic-rg-cube-thimsy-heavy.pac",
 "bytes":7722216910,"sha256":"…","matches_reference":true}
```
- Holds an exclusive lock on `DIR/.thimsy.lock` for the whole build; while
  another build, flash or clean of the workspace holds it, fails with `busy`.
- `--import DIR`: look in DIR for any needed file (matched by name and size,
  then checked by sha256) before downloading. `--import FILE` (a file the
  user picked): the device pack under any name if its size matches, the
  unpacked official firmware under any name if its size matches, anything
  else by name and size. If none of the picked files is used by the build,
  it fails with `bad_input` naming what it expected instead of downloading.
- A device pack published in parts: picked parts are matched to the parts by
  name, then by size in the order picked (so renamed copies work). Once any
  picked file stands for a part, the pack never comes from the network: if
  parts are missing, the build fails with `bad_input` listing them.
- Downloads resume after an interruption or a stall (60 s without data)
  only when `<file>.partial.json` shows the same file from the same server
  (and the server confirms it with `If-Range`); otherwise they start over. A
  resumed download that fails its sha256 check is downloaded once more from
  the start.
- The workspace drive is checked first (as `space` does): `not_enough_space`
  when it's too full; `bad_input` when it's FAT32 (no file over 4 GiB) or
  its free space can't be checked.
- `job.json` records the image's sha256 and each PAC entry's.
- `--set` isn't supported by `build` yet (no build step applies settings):
  it fails with `bad_input`. `resolve --set` still shows the effective
  settings.

### `detect --json [--watch]`
```json
{"type":"devices","devices":[{"vidpid":"1782:4d00","mode":"download","device":null,"label":"Unisoc download mode"}]}
```
`device` is set only when exactly one catalog device uses the ID (the RG Cube
and RG556 share Unisoc's). With `--watch`, a new line is printed whenever the
list changes; runs until killed, or until an `error` line ends it.

### `prepare --job DIR --mode full|update --json`
Gets a finished build ready to install, with no device and no flash tool:
the same image check and partition unpacking/checking `flash` does before
asking for the device (below), under the workspace lock. The app runs it in
the background as soon as `build` finishes, so Install goes straight to the
device prompt. Streams stages `check` and `prepare`. Final:
```json
{"type":"result","ok":true,"files":62,"bytes":7654321234}
```
`files`: the files ready in `DIR/flash`; `bytes`: what the mode writes.
What was checked is recorded in `DIR/flash/prepared.json` (the image and
each unpacked file with its size and modification time). A later
`prepare` or `flash` trusts a check only while that file is unchanged;
anything changed, missing or from another image is read and checked again.
`full` prepares everything `update` needs too.

### `flash --job DIR --mode full|update [--dry-run] --json`
`--mode` is required. `full`: fresh install, every flashable partition
(`partitions_full`), user data erased; NV/calibration partitions are backed up
and never written or erased. `update`: only `partitions_update`; data kept;
the device must already run the matching base (below). Streams stages
`check`, `driver`, `prepare`, `wait_device`, `flash`, `reboot`, with a
`prompt` (`enter_download_mode`) for the physical step. `--dry-run` prints
the tool command as a `log` and in `commands`, and touches no device (and
takes no lock). Final:
```json
{"type":"result","ok":true,"backup":"DIR/backup/run-20261112-171443","commands":["spd_dump --wait 300 …"]}
```
`backup`: this run's backup folder (null on a dry run). `commands`: the tool
command lines run (or that would run).

Before anything is written:
- The workspace lock is taken (`busy` otherwise; the workspace is the folder
  holding `jobs/`), and held until the command ends.
- The image must be the one the current catalog expects for the profile
  (`expect`) and the one `build` recorded (size, sha256 and every PAC
  entry's sha256; progress label `Checking the image`, skipped with a
  `log` when `prepare` checked it and the file is unchanged since);
  otherwise `hash_mismatch` (after an installer update: build again).
- Partitions are unpacked into `DIR/flash` (reused only if they came from
  this exact image), then every file `spd_dump` will write is checked
  against its PAC entry's sha256 (`Checking the partitions`; files
  `prepare` checked and unchanged since aren't read again); one that
  differs is unpacked again once, and if it still differs the command fails
  with `hash_mismatch`.
- `spd_dump` reads the device's partition table into this run's backup
  folder (`DIR/backup/run-<time>/device-partitions.xml`) and `device.json`
  is written next to it. Every partition to be backed up, written, erased
  or compared must be in the firmware's partition table and exist on the
  device with that size (names compared ignoring case); otherwise nothing is
  confirmed, nothing is written, and the command fails with `wrong_device`
  (another model on the same USB ID, or a stock layout that needs
  repartitioning, which this version doesn't do). The only partitions
  written without this check are the ones the recipe lists in
  `unchecked_partitions` (boot-area loaders such as `splloader`, which the
  table doesn't contain).
- Every backup must have been read at the partition's full size; otherwise
  nothing is confirmed and the command fails with `tool_failed`.
- `update` only: the images the update relies on but doesn't write (the
  recipe's `update_check`: for the RG Cube boot, init_boot, dtb, dtbo and
  every vbmeta, both slots) are read back from the device at their PAC
  entry's size and compared with the PAC. Any difference: nothing is
  confirmed, nothing is written, and the command fails with
  `full_install_needed` naming the partitions (the device doesn't run a
  matching Thimsy or GammaOS base; offer a full install). The images read
  for this aren't kept.
- `spd_dump` gets each "yes" only when it asks, so if the engine is stopped
  (the app's Cancel kills it) no further write can be confirmed. Only the
  bundled `spd_dump` is used (from the installer's tools folder, never PATH;
  `THIMSY_TOOLS_DIR` is honoured only by test builds). On Linux and Windows
  `spd_dump` is also killed with the engine (Windows: it joins a
  kill-on-close job before it starts); on Linux and macOS SIGTERM, SIGINT and
  SIGHUP kill it before the engine exits.
- If the app goes away (writing an event to it fails, or on Linux and macOS
  the engine gets a new parent process) before the first "yes", `spd_dump`
  is killed and the engine stops (`cancelled`). After that the flash runs to
  its end: stopping in the middle of a partition is worse, and every further
  write still needs its own confirmation from the checked plan.

Errors while flashing:
- `device_not_found`: `spd_dump` gave up without the device ever answering
  in download mode (nothing was written). The hint says to repeat the
  download-mode steps (on Windows also to check the WinUSB driver); on Linux,
  when the device is connected but couldn't be opened, it says to set up USB
  access (`drivers --install`).
- `tool_failed` (the tool is killed at once) when `spd_dump` reports a
  partial write (`load_partition: …, target: T, written: W` with W ≠ T),
  logs `unexpected response`, or writes anything before the checks above
  passed. At the end it fails unless every planned partition was reported
  written in full, and unless `spd_dump` asked to confirm every write and
  erase. Only once the first write was confirmed does the message start with
  "flashing stopped; the device is still recoverable from download mode".

Backups go straight to a new folder per run, `DIR/backup/run-<UTC
time>/<partition>.img` (the final `backup` field), outside the scratch
folder, so nothing moves, replaces or deletes them. They are whole
partitions and are kept even when flashing fails; one of the wrong size gets
`.incomplete` added (and the command fails). The folder also holds
`device-partitions.xml` and `device.json` (`device`, `device_name`,
`partition_table_sha256`, `time`, `mode`, `engine`).

### `unlock --device ID --json`
For devices whose unlock is `automated` (fastboot `flashing unlock` with
on-device confirmation). For `guided` devices it returns
`{"type":"result","ok":false,...}` with code `unlock_guided`; the app shows
`guides.unlock` instead.

### `drivers --device ID [--install] --json`
```json
{"type":"result","ok":true,"status":"ok|missing|not_required","detail":"…"}
```
`detail` is translated.
- Windows: `ok` when the driver store has a WinUSB package for every
  download-mode ID of the device; `missing` otherwise. `--install` installs
  WinUSB behind one UAC prompt: an elevated, hidden Windows PowerShell (by
  absolute path) copies the bundled `wdi-simple.exe` into a fresh
  administrators-only folder under ProgramData, checks its sha256, runs it
  there for each ID and removes the folder; afterwards every ID must be in
  the driver store. `flash` does the same in its `driver` stage when needed.
- Linux: `ok` when the engine runs as root or a udev rule in
  `/etc/udev/rules.d`, `/usr/lib/udev/rules.d` or `/lib/udev/rules.d`
  matches each ID (vendor and product on one line); `missing` otherwise.
  `--install` writes `/etc/udev/rules.d/70-thimsy-installer.rules`
  (`TAG+="uaccess"` for each ID) and reloads udev through `pkexec` (one
  password prompt). `flash` only warns (in a `log`) when it's missing.
- macOS and other hosts: `not_required`.

A failed `drivers` ends with the current state:
```json
{"type":"error","code":"tool_failed","message":"driver install for … failed (the Windows permission prompt was declined)","hint":"…"}
{"type":"result","ok":false,"status":"missing","detail":"…"}
```
(`status`/`detail` are left out only when the device itself is unknown.)

## Error codes
`device_not_found`, `wrong_device`, `full_install_needed`, `download_failed`,
`hash_mismatch`, `not_enough_space`, `busy`, `tool_missing`, `tool_failed`,
`unsupported_host`, `profile_unavailable`, `unlock_guided`, `cancelled`,
`bad_input`, `internal`.

- `device_not_found`: the device never answered in its flashing mode (or, on
  Linux, couldn't be opened); nothing was written.
- `wrong_device`: the connected device's partition table doesn't match the
  firmware; nothing was written.
- `full_install_needed`: `flash --mode update` on a device that doesn't run
  the matching base; nothing was written. Offer `--mode full`.
- `busy`: another build, flash or clean is using the workspace (its
  `.thimsy.lock`); nothing was done. Wait, or use another workspace.
- `not_enough_space`: the workspace drive is too full.
- `bad_input`: the command line asked for something this version can't do
  (e.g. `build --set`), picked files the build can't use or a device pack
  with parts missing, a `clean --path` that isn't a cleanable item, or a
  workspace on a FAT32 drive or one whose free space can't be checked.
- `cancelled`: the app went away before the first write was confirmed.
